### Exit criterion (fix round 1)

The check passes when all of these hold (`FlacLibraryCheckTest.gateFailures`):

- **MISMATCH is 0.** No file decodes to audio that disagrees with its MD5.
- **Every ERROR is damage the decoder proved from the bytes, classified by the exception's type, never by its
  message.** `FlacDamageException` carries a `Kind`, and `FlacVerify.Result.damage()` exposes it (null for anything
  that is not proven damage; `Status` is unchanged):

  | Kind | Proof |
  |---|---|
  | `CRC_MISMATCH` | a frame's CRC-8 (header) or CRC-16 does not match its bytes |
  | `NOT_FLAC` | no `fLaC` marker (or too few bytes to hold one) |
  | `OVERSIZED_FRAME` | a frame that does not end within 2× STREAMINFO maxFrame (never less than 64 KiB), or no frame sync where the next frame must start |
  | `TRUNCATED` | the file ends inside the metadata, inside a frame, or before the samples STREAMINFO promises |

  A `RuntimeException`, an I/O fault, any other `DecodeException` (a reserved field value, a different sample rate),
  and a root that does not exist are ERRORs that are **not** damage, and fail the check. A missing root is counted as
  an ERROR (and `FlacVerify.main` exits 1 for it), so an unmounted drive cannot pass as a clean scan of nothing.
- **Enough files were checked.** At least one file was checked, and OK is at least `-Dpurist.libraryMinOk` (default
  1185, this library's count), so a decoder regression cannot hide as "damage".

The run prints the counts, the number of proven-damage files per kind, and every non-OK file with its kind and
detail.

Expected result for this library: `1185 OK, 0 MISMATCH, 10 NO_MD5, 26 ERROR`, with the 26 ERRORs being 17 `NOT_FLAC`,
7 `OVERSIZED_FRAME` and 2 `CRC_MISMATCH`. Confirmed on 2026-10-22 without repeating the 36-minute pass, by running
`FlacVerify` (read-only) over the Postal Service folder, the Tool Undertow folder and the Yosi Horikawa folder: the 17
zero-prefixed files report `NOT_FLAC`, the 7 files with a zero-filled hole report `OVERSIZED_FRAME`, the 2 Undertow
files report `CRC_MISMATCH`, the others are OK, and a mistyped root reports an ERROR with no kind and exit status 1.
The decode logic did not change, so the full pass was not repeated; the classification is covered by unit tests that
craft each kind with `FlacWriter`.

One real-world quirk was found and handled: 8 files of `Yosi Horikawa FLAC\2012 Touch` have (in the two inspected) a second
padding-block header and 1,024 zero bytes between the last metadata block and the first frame (a tagger left them behind). The
decoder looks for the first frame in the next megabyte and starts there if it is frame 0, and all 44 files of that
folder verify OK.
